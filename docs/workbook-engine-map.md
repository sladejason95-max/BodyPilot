# Weight and macro workbook engine

`src/app/weight_macro_engine.ts` is a deterministic planning-model translation of the supplied **Weight & Macro Tracker** worksheet. It does not accept a recommendation, edit a food log, change a bodyweight observation, or claim that estimated expenditure is measured physiology. All fixtures use synthetic people and dates; the supplied athlete's personal details are not application defaults.

## Integration contract

- `calculateWeightMacroTracker(settings, records, weeklyOverrides, asOfDate, options?)` returns validation, compatibility diagnostics, derived setup values, initial macros, daily rows, weekly rows, and dashboard data. An explicit `YYYY-MM-DD` as-of date replaces `TODAY()`.
- `options.acceptedWeeklyTargets` can anchor a week's current calories/macros to the application's immutable acceptance ledger. Without that option, the workbook's normal previous-next-week chaining is retained. Anchoring changes the current targets used for adherence and proposals, never logged actuals.
- `nextWeightMacroTargets(settings, current, endingTrend, nextCalories)` allocates a chosen calorie proposal, including recommendation-only mode. `weightMacroDailyTarget(settings, weeklyMacros, dayType)` applies the same daily cycling formulas to frozen revisions.
- `WEIGHT_MACRO_OPTIONS` and `WEIGHT_MACRO_SETTING_FIELDS` supply option labels, input types, fractional percentage metadata, and workbook references. Boolean settings represent workbook Yes/No and On/Off choices. Weight-dependent inputs are expressed in the selected `lb` or `kg` unit; the engine does not silently convert them.
- `createWeightMacroSettings` requires the caller's start date, starting weight, goal weight and calorie target. Its other defaults are configurable starting configuration, not a recommendation or an inferred readiness assessment.
- Each daily row exposes all A:AH cells. Each weekly row exposes all AI:CL cells plus its workbook row, formula references, hold rule, explanation, diagnostics, and observation coverage. Dates are strings rather than Excel serial numbers. Empty formula results are `null`, not zero.
- Weekly evidence lists the week's observation IDs/dates and separate `trendRecordIds`/`trendDates` including earlier days needed by the active rate. `isComplete` describes whether the review interval has elapsed; it is not an automatic approval signal. Smoothed expenditure also depends on earlier weekly outputs.

## Formula coverage

- B3:B36, E3/E5/E7:E22 and H3:H9 are configurable inputs. E4/E6 calculate lean mass; B37:B42 provide signed target rate, percentage, projection, planning status, first review date and current week. E25:E30 calculate initial macros, macro energy, setup status and allocation explanation. H10:H14 reconcile cycling targets. G17 provides the current recommendation text.
- A:D generate calendar dates, day names, first-partial-week numbering and weekday-derived day type. E/F and Q:T/W:AD are explicit observations. G is a seven-calendar-day average requiring three included positive weigh-ins. H carries an exponentially weighted trend from the first included positive observation. I requires four observations and fits a regression against actual calendar offsets: rows 46:59 expand; row 60 uses 47:60; later rows retain exactly 14 calendar rows. J selects the configured trend, K:L derive trajectory/error, M:P allocate daily targets, U:V calculate adherence, AE:AF show maintenance bounds, and AG:AH detect previous-included-weight changes and preserve included weights.
- AI:AK generate up to 53 reviews, with a partial first or final week where needed. AL:AP calculate valid counts, raw average, ending selected trend and week-to-week change. AQ subtracts regression endpoints seven days apart. AR:AU compare rate and trajectory. AV:BG calculate positive-logged-value averages and completeness-adjusted nutrition adherence.
- BH estimates expenditure as average intake minus weekly weight change times **3,500 per lb / 7,700 per kg**, divided by seven. This is workbook arithmetic, not a medical claim. BH requires enough weigh-ins, at least four calorie days, and sufficient adherence. BI smooths reliable estimates with 35% current and 65% prior, carrying the last estimate through unreliable weeks.
- BJ:BM hold the week's current calorie/macronutrient targets. BN converts rate error to energy and applies aggressiveness. BO requires two consecutive same-side trajectory errors outside tolerance, then caps the correction. BP first applies hold rules, ignores changes smaller than one calorie increment, rounds, and caps the signed weekly adjustment. BQ clamps the recommended next target to calorie limits. BR is an explicit override; BS applies fixed-macro, manual-override, automatic, or non-automatic behavior in workbook order.
- BT:BV and CG:CI calculate next protein, non-protein calorie delta, priority-based fat allocation, fat/carbohydrate floors and macro rounding. CL detects impossible protein/floor allocations; CK reports actual macro energy. All six macro modes, five protein bases, three increase/decrease priorities, protein hold choices, and cycling protein/fat branches are covered.
- BW:BX calculate sample weight variability and daily-change/sodium-context anomaly flags. BY, CA and CD remain context inputs. BZ summarizes refeed context. CB:CC explain the result. CE chooses a valid regression rate before the week-to-week fallback; CF is target minus actual rate.
- CJ preserves the source precedence: goal reached → goal date passed → explicit hold → fixed macros → manual mode → insufficient history → observation period → low weigh-ins → poor adherence → noisy data → water anomaly → maintenance range → rate deadband.
- Dashboard data replaces formatted text and sparklines with typed values: latest observations and trends, progress, 7/14/28-day changes, rate percentages, trajectory timing, current/recommended calories, macros, reliable expenditure, adherence, weigh-in coverage, projected goal date, waist context, 30-day trend and daily adherence series.

## Explicit compatibility and safety choices

1. **AQ blank arithmetic:** Excel subtraction coerces matched empty regression cells to zero, which can fabricate a zero or enormous weekly rate. This implementation returns unknown unless both endpoints exist, records `AQ_BLANK_REGRESSION`, and uses a valid week-to-week fallback. Dashboard change calculations likewise do not subtract a missing trend as zero.
2. **As-of boundary:** the worksheet can carry EW trends or extrapolate regression into future generated rows, then show those rows through unbounded `LOOKUP`. This model only calculates observation-derived trends through `asOfDate`. Future rows retain planned targets but are never measurement evidence. Submitted future observations are excluded with diagnostics. No future data are used to backfill an earlier week.
3. **Daily vs weekly carbohydrate:** daily O always uses the calorie remainder, even when the initial weekly BL stores configured percentage/fixed carbohydrate. Weekly BU also uses the remainder outside fixed-all mode. The different outputs are preserved; mismatches are explicitly reported. No calorie or macro residual is hidden.
4. **Fixed-all override message:** source BS ignores calorie overrides in fixed-all mode, while CB/CC claim an override was applied. The numeric rule is preserved, but the displayed status correctly identifies fixed macros and reports the ignored override.
5. **Floor/rounding mismatch:** source BV rounds fat downward after applying floors. A floor not aligned to the increment can therefore be breached. Arithmetic is preserved with a warning. Daily M:P can also breach weekly calorie/macro limits; those conditions are reported, not silently clamped, because clamping would break source parity and cycling reconciliation.
6. **Missing/invalid data:** absent lean-mass inputs do not become zero protein. Invalid numbers/dates, ambiguous duplicate dates/overrides, and future observations are excluded or fail validation rather than producing fabricated measurements. Zero actual intake is retained as an explicit daily value, but the workbook's weekly positive-value averaging/counting remains unchanged. Unrepresentable projected dates return unknown with a diagnostic.
7. **Warnings are not invented rules:** B32 is a planning warning, not a hard rate cap. Deload/travel/notes are context, not source hold rules. Initial calorie targets may be outside limits; BQ clamps the next target even under a hold. Fixed-all macro calories override calorie bounds. All are exposed so the application acceptance policy can require review.
8. **Incomplete review:** `evidence.isComplete` is separate from CJ. The workbook can produce a provisional numeric recommendation before the review ends. Application policy must prevent that preview from silently changing accepted targets.

Tests exercise settings/column coverage, date boundaries, all hold/mode branches, rounding, blank/future/duplicate data, regression windows, expenditure, cycling reconciliation, accepted targets and proposal allocation. The engine has no storage, clock, network or application-state dependencies.

## Independent arithmetic check

A separate spreadsheet-runtime recalculation used synthetic starting weight, goals, macros and 35 daily records. All **837 numeric daily/weekly cell comparisons matched within 1e-7**. The imported runtime retained the original cached first date in A46 after changing B4; the audit replaced A46's first-row expression with its algebraic equivalent `=$B$4` to force that cell to recalculate. The original supplied workbook was not modified. This check covers that synthetic scenario, not every possible input combination; branch tests and the compatibility choices above remain necessary.
